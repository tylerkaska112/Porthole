# 0170 Wine: write the new load address into the header's ImageBase after relocating an image (BO3 experiment)

`vendor/Madeira/build/ntdll-unix/virtual_ios.c` (`git -C vendor/Madeira apply patches/0170-wine-header-imagebase-after-relocation.patch`), `virtual_relocate_module`: with `MADEIRA_FIX_IMAGEBASE=<exe file name>` (only that exe; value 1 hit the Steam client too and broke its sign-in, 1.2.40) the mapped header's `OptionalHeader.ImageBase` becomes the load address once the relocations are applied, as Windows does (Wine already does it for ASLR images, `relocate to dynamic base`). The relocation of the main exe is actually done by the PE-side loader (ntdll `perform_relocations`, 1.2.39 log: the `virtual_relocate_module` hook never fired), so the effective hook is in `server_init_process_done` (`server_ios.c`): it rewrites the main exe's header ImageBase from `Peb->ImageBaseAddress` just before the first guest instruction. Off by default; `[imagebase] 0170: header ImageBase A -> B` is logged when it fires.

Why: Black Ops III's 491 MB exe cannot get 0x140000000 (the RX pool is there) and is relocated to 0x70xxxxxxxx; its Arxan guards end in a dead-end state ring (closed 41-state machine, exit state never reached = a check upstream produced a wrong state value). Code that reads its own header sees "never relocated" on our side.

Rebuild: `F4_BUILD_ROOT=… BASE=…/gl-lib-0163/libntdll_unix.a OUT=…/gl-lib-0170 tools/rebuild_ntdll_object.sh virtual`, then `BASE=…/gl-lib-0170/libntdll_unix.a OUT=…/gl-lib-0170e … server`; symlink the other libs of gl-lib-0163 beside it and point `stage-head/lib/libntdll_unix.a` at gl-lib-0170e. (The `obj` folder of gl-lib-0170 is a symlink into gl-lib-0163: virtual.o there was overwritten too.) Unverified on a device.

1.2.42 adds a section table and a few probe dumps to the `[imagebase] 0170` log lines (what the file declares per section, and the first 16 bytes memory holds there), to tell file-backed sections from BSS.

1.2.43 adds a `[data-watch]` thread for the named exe: at +3, 8, 14, 20, 26, 32 s after start it logs the runs of non-zero 4 KB pages in the exe's largest non-code section (BO3: .data, 370 MB mostly BSS), to see where the game's self-unpacking writes. Finding (1.2.42 log): .data raw size is 0x3a3600 of vsize 0x175d6360; the packed .text sections are ciphertext at start; the game later jumps to exe+0x14deaea1 (BSS, zeros) = the unpacker's output is missing there.
