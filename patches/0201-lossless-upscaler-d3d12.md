# 0201: Lossless Scaling's upscaler (LS1, LS1 performance) for Direct3D 12 games

The Direct3D 11 swap chain (0200) enlarges the game's frame itself. A Direct3D 12 game presents through madeira_d3d12.dll with Metal directly, so the passes run on the bridge device in d3d11.dll (the same arrangement as the frame generation bridge, 0191) and the two sides join through Metal shared events.
- `DXMTUpscaleBegin/Run/Abort/Failed` (d3d11_lsfg_bridge.cpp, struct DXMTUpscaleFrame = madeira_d3d12.c struct upscale_bridge_frame): Begin decides and (re)builds an `Ls1Upscaler` for the game's size / the output size / method / level, hands out the Metal texture the game's picture is copied into; Run waits for that copy (input fence) and for the previous enlarged picture to have been copied out (done fence), runs the passes, signals the out fence and returns the enlarged picture's Metal texture + events.
- madeira_d3d12.c `mad_up_before` (before the generated pictures and the real present): blit src -> bridge input, signal, Run; the first 8 frames wait on the CPU for the passes (<= 40 ms; the shaders are compiled then), later the present's own command buffer waits on the GPU (`encodeWaitForEvent`), and signals the done event after its blit. Not available / failed (the bridge says so through DXMTUpscaleFailed) -> MetalFX as before, and the status file says `fallback=`.
- The generated pictures of the frame generation bridge are enlarged by the same upscaler inside DXMTLsfgRun (`out_width/out_height` in the frame struct tell Present they already are the big size).
- Control file keys `method`, `level` are read by the PE too (`g_up_method`, `g_up_level`); status via `mad_up_write_status`.
Output size = the MetalFX path's `fx_w x fx_h` (the factor, even sizes), so the layer's drawable size is unchanged. Not verified on a device. `tools/engine.sh accept`.
